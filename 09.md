NWC-09
======

Payment Lookup
--------------

`draft` `optional`

## Summary

This specification defines the optional, payment-type-neutral `lookup_payment` method and a common payment record envelope for Nostr Wallet Connect.

It also defines the `bolt11` payment type because BOLT11 invoices and `lookup_invoice` are part of NWC core in NIP-47. Every other payment type and its `details` object are defined by a separate optional NWC extension.

For payment types other than `bolt11`, payment-type extensions define:

- `payment_type` values
- type-specific lookup selectors
- the contents of `details`
- type-specific state and settlement rules

This separation lets applications reconcile payments without requiring this specification to change whenever NWC supports another Bitcoin payment protocol.

## Motivation

Applications need to reconcile a payment after a timeout, reconnect, retry, or missed notification. The lookup operation and its common result fields are the same regardless of how the wallet sent or received the payment.

Protocol-specific identifiers and proofs do not belong in a universal field bag. Keeping them in a discriminated `details` object avoids unused fields, naming collisions, and changes to this specification for each new payment protocol.

## Discovery

A wallet service supporting this specification MUST advertise `lookup_payment` as a supported method in its NWC info event and `get_info` response.

The wallet service SHOULD also advertise `09` according to NWC core extension discovery.

An implementation of this specification MUST support `bolt11`. Support for `lookup_payment` does not imply support for any other payment type. A wallet service MUST also advertise each supported payment-type extension as required by that extension.

## Method

### `lookup_payment`

Looks up one payment record visible to the requesting connection.

The generic selector is the stable wallet-scoped `transaction_id` returned by other NWC methods:

```yaml
{
    "method": "lookup_payment",
    "params": {
        "transaction_id": "wallet-scoped-id"
    }
}
```

All implementations of this specification MUST support lookup by `transaction_id`.

Payment-type extensions MAY define additional selectors. An extension-defined lookup uses this request shape:

```yaml
{
    "method": "lookup_payment",
    "params": {
        "payment_type": "extension_defined_type",
        "lookup": {
            // extension-defined selector fields
        }
    }
}
```

A request MUST use exactly one of these forms:

- `transaction_id`
- the BOLT11-compatible top-level `payment_hash` and/or `invoice` fields defined below
- both `payment_type` and `lookup` for a payment type defined by another extension

Except for the BOLT11 compatibility fields, type-specific selector fields MUST be placed inside `lookup`, not directly inside `params`.

The wallet service MUST match selectors only against records visible to the requesting connection. It MUST NOT reveal whether an inaccessible record exists.

Every successful lookup MUST resolve to exactly one payment record. A wallet service MUST NOT select an arbitrary record when a selector matches multiple payments.

Response:

```yaml
{
    "result_type": "lookup_payment",
    "result": {
        "transaction_id": "wallet-scoped-id", // stable identifier for this payment record
        "type": "outgoing", // "incoming" or "outgoing"
        "state": "settled", // generic payment state
        "payment_type": "extension_defined_type",
        "amount": 123000, // payment amount in msats
        "fees_paid": 1000, // fees attributed to this payment in msats, optional
        "created_at": unixtimestamp, // wallet record creation time
        "updated_at": unixtimestamp, // last material record update time, optional
        "expires_at": unixtimestamp, // payment expiration time, optional
        "settled_at": unixtimestamp, // time the wallet moved the record to "settled", optional
        "failure_reason": "string", // optional unless state is "failed"
        "metadata": {}, // optional metadata as defined in 06.md
        "details": {} // required object defined below for BOLT11 or by a payment-type extension
    }
}
```

All fields not explicitly marked optional are REQUIRED.

`transaction_id` MUST be stable within the wallet service and MUST identify the same payment in responses from other NWC methods. It identifies one payment record and does not necessarily identify an underlying protocol object or an entire on-chain transaction.

`amount` and `fees_paid` use millisatoshis for every payment type. The BOLT11 definition below and every payment-type extension MUST specify how native amount and fee units map to millisatoshis.

`fees_paid` is the fee attributed by the wallet to this payment. It MAY be omitted when the fee is unavailable or cannot be meaningfully allocated.

`details` MUST contain only fields defined below for `bolt11` or by the extension for another `payment_type`. Common fields MUST NOT be duplicated inside `details`. Clients MUST ignore unknown fields in `details` to permit backward-compatible additions.

## Payment states

Payment records MUST use one of these states:

- `pending`: The payment exists but has not reached the wallet's settlement policy.
- `accepted`: Funds are committed but settlement has been deliberately held.
- `settled`: The wallet considers the payment final under its policy.
- `failed`: An outgoing payment attempt ended unsuccessfully.
- `expired`: The payment request expired without settlement.
- `canceled`: The payment or payment request was canceled.

The BOLT11 definition below and every payment-type extension MUST define which states apply and what causes transitions between them. A payment-type extension MAY restrict this list but MUST NOT define additional states without an extension to this specification.

## BOLT11 payment type

This specification defines `bolt11` directly using the BOLT11 invoice and payment fields already established by [NIP-47](https://github.com/nostr-protocol/nips/blob/master/47.md) and [BOLT11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md).

### Lookup selectors

In addition to generic lookup by `transaction_id`, a BOLT11 payment can be looked up using the same top-level parameters as NIP-47 `lookup_invoice`. The absence of `payment_type` implies `bolt11` for this request form.

Request:

```yaml
{
    "method": "lookup_payment",
    "params": {
        "payment_hash": "31afdf1..", // payment hash of the invoice, one of payment_hash or invoice is required
        "invoice": "lnbc50n1..." // invoice to lookup
    }
}
```

The request MUST contain at least one of:

- `payment_hash`: the 32-byte invoice payment hash encoded as lowercase hex
- `invoice`: the encoded BOLT11 invoice

If both are present, they MUST identify the same BOLT11 invoice. The wallet MUST return `BAD_REQUEST` if they conflict.

If a selector matches multiple wallet-visible records, the wallet MUST return `MULTIPLE_MATCHES`.

### Payment details

A successful BOLT11 lookup uses the common response envelope with `payment_type` set to `bolt11` and this `details` object:

```yaml
{
    "payment_hash": "31afdf1c...", // 32-byte invoice payment hash
    "invoice": "lnbc50n1...", // encoded BOLT11 invoice, optional
    "preimage": "0123456789abcdef...", // 32-byte payment preimage, optional
    "description": "string", // invoice description, optional
    "description_hash": "abcdef..." // invoice description hash, optional
}
```

`payment_hash` is REQUIRED. `invoice` SHOULD be returned when retained by the wallet. `preimage` SHOULD be returned for a settled payment when available.

The wallet MUST NOT return `preimage` unless SHA-256 of it equals `payment_hash`.

The common `amount` and `fees_paid` fields are the BOLT11 payment amount and routing fees in millisatoshis.

The applicable states are `pending`, `accepted`, `settled`, `failed`, `expired`, and `canceled`. `accepted` is used for an accepted hold invoice that has not been settled or canceled. `settled` means the Lightning payment completed and the wallet considers it final.

## Payment-type extension requirements

Every payment type other than `bolt11` MUST be defined by a separate optional NWC extension. An extension defining a payment type MUST:

1. Define a lowercase `snake_case` `payment_type` value.
2. Define the required and optional fields in `details`.
3. Define how native amounts and fees map to the common millisatoshi fields.
4. Define applicable states and settlement semantics.
5. Define any additional selector forms inside `lookup` and their uniqueness rules.
6. Define any relevant privacy, disclosure, replay, or chain-reorganization behavior.
7. State how support for the payment type is discovered.

Payment-type values are scoped by their defining NWC extension. Two extensions MUST NOT define incompatible meanings for the same value.

## Errors

- `BAD_REQUEST`: The request shape, selector, or identifier is invalid.
- `NOT_FOUND`: No payment visible to this connection matches the selector.
- `MULTIPLE_MATCHES`: More than one payment visible to this connection matches the selector. The client should retry with `transaction_id` or a more specific extension-defined selector.
- `UNSUPPORTED_PAYMENT_TYPE`: The wallet does not support the requested `payment_type` for this connection.

The wallet service can also return applicable NWC core errors.

## Relationship to other specs

- NWC core `lookup_invoice` remains available for BOLT11-specific compatibility.
- [05.md](05.md) defines `list_transactions` and allows payment-type extensions to reuse the payment record envelope defined here.
- [06.md](06.md) defines metadata conventions for the optional `metadata` field.
- [12.md](12.md) defines BOLT12 offers and the `bolt12` payment type for `lookup_payment`.
- [321.md](321.md) defines BIP-321 `pay` and `receive`. A `transaction_id` returned by that specification MUST identify the same payment record when used with `lookup_payment`.
- [02.md](02.md) notifications are state-change hints. Clients can use `lookup_payment` to reconcile the authoritative current record after receiving or missing a notification.
