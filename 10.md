NWC-10
======

BOLT12 Offers
-------------

`draft` `optional`

## Summary

This specification defines BOLT12 offer support for Nostr Wallet Connect.

It includes:

- creating or retrieving a BOLT12 offer with `make_offer`
- keeping returned offers payable while the user-facing wallet is offline
- the `bolt12` payment type, selectors, and `details` object for `lookup_payment` in [09.md](09.md)

## Motivation

BOLT12 offers provide reusable and variable-amount Lightning receive targets. They also support invoice requests, payer notes, quantities, blinded paths, and payer proofs that are not represented by BOLT11-specific NWC methods.

Applications sometimes need to request BOLT12 explicitly instead of allowing a wallet to select among several BIP-321 payment instructions. They also need to reconcile the resulting payments through the payment-type-neutral `lookup_payment` method.

## Dependencies

Implementations use:

- [09.md](09.md) for the generic `lookup_payment` method and common payment record envelope
- [06.md](06.md) for metadata conventions
- [BIP-321](https://github.com/bitcoin/bips/blob/master/bip-0321.mediawiki) for the returned Bitcoin payment URI
- [BOLT12](https://github.com/lightning/bolts/blob/master/12-offer-encoding.md) for offers, invoice requests, invoices, and payer proofs

## Discovery

A wallet service supporting this specification MUST:

- advertise `make_offer` and `lookup_payment` as supported methods in its NWC info event and `get_info` response
- advertise `09` and `10` according to NWC core extension discovery
- support `bolt12` as a `payment_type` for `lookup_payment`

## Methods

### `make_offer`

Creates or returns a BOLT12 offer usable as a receive target.

Request:

```yaml
{
    "method": "make_offer",
    "params": {
        "amount": 123000, // amount per payment in msats, optional; null or omitted for variable amount
        "description": "string", // offer description, optional for variable-amount offers
        "issuer": "example.com", // human-readable issuer, optional
        "single_use": false, // request at most one settled payment, optional; default false
        "expires_at": unixtimestamp, // absolute offer expiry, optional
        "metadata": {} // optional metadata as defined in 06.md
    }
}
```

`amount` MUST be a positive integer when present and non-null. If `amount` is present and non-null, `description` is REQUIRED because BOLT12 requires an amount-bearing offer to describe the purpose of the payment.

`expires_at` MUST be a future Unix timestamp when present. The wallet MUST encode it as the BOLT12 absolute expiry and MUST stop answering invoice requests after it.

`issuer`, when present, MUST be encoded as the BOLT12 issuer. The wallet MUST NOT silently replace a non-empty `description` or `issuer` supplied by the client.

If `single_use` is true, the wallet MUST enforce that at most one payment created from the returned offer settles. It SHOULD stop issuing new invoices while an earlier invoice from that offer can still settle. `single_use` is wallet-enforced policy; it is not an intrinsic property of the encoded BOLT12 offer.

Response:

```yaml
{
    "result_type": "make_offer",
    "result": {
        "offer_id": "0123456789abcdef...", // 32-byte BOLT12 offer ID encoded as lowercase hex
        "bip321": "bitcoin:?lno=lno1...", // BIP-321 URI containing the offer
        "offer": "lno1...", // raw BOLT12 offer, optional
        "amount": 123000, // amount in msats, or null for a variable-amount offer
        "description": "string", // encoded offer description, optional
        "issuer": "example.com", // encoded offer issuer, optional
        "single_use": false,
        "created_at": unixtimestamp,
        "expires_at": unixtimestamp // optional
    }
}
```

All response fields not explicitly marked optional are REQUIRED. The `bip321` value MUST contain exactly one `lno` parameter for the returned offer. If `offer` is also present, it MUST encode the same offer.

The wallet MAY return an existing offer only when its amount, description, issuer, `single_use` policy, expiry, metadata association, network, and visibility to the requesting connection satisfy the request.

The wallet MUST support reusable variable-amount offers, requested by omitting `amount` or setting it to null while leaving `single_use` false.

The wallet MUST keep every unexpired offer returned by `make_offer` payable while the user-facing wallet application is offline. This requires an always-online wallet service or a BOLT12 async-payment mechanism. Interactive-only receive support is not sufficient.

The wallet SHOULD associate request `metadata` with payments received through the returned offer. When it does, that metadata is returned in the common `metadata` field of the corresponding `lookup_payment` record.

Errors:

- `BAD_REQUEST`: A parameter is invalid or cannot be represented by a valid BOLT12 offer.
- `TEMPORARILY_UNAVAILABLE`: The wallet cannot create or keep the offer payable at this time.

The wallet service can also return applicable NWC core errors.

### `lookup_payment`

This specification defines `bolt12` as a payment type for the generic method in [09.md](09.md).

In addition to generic lookup by `transaction_id`, a BOLT12 payment can be looked up by payment hash, invoice, or offer ID.

Request by offer ID and payment hash:

```yaml
{
    "method": "lookup_payment",
    "params": {
        "payment_type": "bolt12",
        "lookup": {
            "offer_id": "0123456789abcdef...",
            "payment_hash": "31afdf1c..."
        }
    }
}
```

The `lookup` object MUST use exactly one of these selector forms:

- `payment_hash`: the 32-byte invoice payment hash encoded as lowercase hex
- `invoice`: the encoded BOLT12 invoice
- `offer_id`, optionally qualified by `payment_hash`: the 32-byte BOLT12 offer ID encoded as lowercase hex

A BOLT12 offer can be reusable, so `offer_id` alone is not guaranteed to identify one payment. If a selector matches multiple wallet-visible records, the wallet MUST return `MULTIPLE_MATCHES`. Clients SHOULD retain `transaction_id` or combine `offer_id` with `payment_hash` for later lookup.

Response:

```yaml
{
    "result_type": "lookup_payment",
    "result": {
        "transaction_id": "wallet-scoped-id",
        "type": "incoming", // "incoming" or "outgoing"
        "state": "settled", // "pending", "settled", "failed", "expired", or "canceled"
        "payment_type": "bolt12",
        "amount": 123000, // invoice amount in msats
        "fees_paid": 1000, // routing fees in msats, optional
        "created_at": unixtimestamp,
        "updated_at": unixtimestamp, // optional
        "expires_at": unixtimestamp, // invoice expiration time, optional
        "settled_at": unixtimestamp, // optional unless state is "settled"
        "failure_reason": "string", // optional unless state is "failed"
        "metadata": {}, // optional metadata as defined in 06.md
        "details": {
            "payment_hash": "31afdf1c...", // 32-byte invoice payment hash
            "invoice": "lni1...", // paid BOLT12 invoice, optional
            "invoice_request": "lnr1...", // BOLT12 invoice request, optional
            "offer_id": "0123456789abcdef...", // BOLT12 offer ID, required for offer-derived payments
            "offer": "lno1...", // BOLT12 offer, optional
            "preimage": "0123456789abcdef...", // 32-byte payment preimage, optional
            "payer_proof": "lnp1...", // BOLT12 payer proof, optional
            "payer_note": "string", // payer-provided note, optional
            "quantity": 1, // purchased quantity, optional
            "description": "string", // offer or invoice description, optional
            "issuer": "example.com" // offer issuer, optional
        }
    }
}
```

The common fields follow [09.md](09.md). Within `details`:

- `payment_hash` is REQUIRED.
- `offer_id` is REQUIRED when the payment was created from an offer.
- `invoice` SHOULD be returned when retained by the wallet.
- `invoice_request`, `offer`, `preimage`, `payer_proof`, `payer_note`, `quantity`, `description`, and `issuer` are optional and MUST represent the objects and values used for this payment.
- `preimage` MUST NOT be returned unless SHA-256 of it equals `payment_hash`.
- `payer_proof`, when returned, MUST be a valid BOLT12 payer proof for this payment.
- `payer_note` MUST NOT be synthesized or modified by the wallet.

Invoice requests and payer proofs can contain payer-specific information. A wallet MUST return them only when visible to the requesting connection and SHOULD omit them when they are not needed by that application's payment flow.

## Payment states and amounts

The applicable states for `bolt12` records are `pending`, `settled`, `failed`, `expired`, and `canceled`.

`settled` means the Lightning payment completed and the wallet considers it final. The common `amount` is the BOLT12 invoice amount in millisatoshis. The optional common `fees_paid` is the routing fee attributed to the payment in millisatoshis.

An offer is a receive target, not a payment record. `offer_id` therefore does not replace the common `transaction_id`, and calling `make_offer` does not itself create a record that can be returned by `lookup_payment`.

## Relationship to other specs

- [09.md](09.md) defines the generic payment lookup envelope used by the `bolt12` payment type.
- [321.md](321.md) defines generic BIP-321 `pay` and `receive`. Clients that require a BOLT12 offer specifically use `make_offer` from this specification.
- [02.md](02.md) defines payment notifications. Notifications are state-change hints; clients use `lookup_payment` to reconcile the current BOLT12 payment record.
