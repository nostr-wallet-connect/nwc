NWC-08
======

Client-Initiated Connection Creation
------------------------------------

`draft` `optional`

## Summary

This specification defines "1-click" connection flows where the **client** generates its own secret and only public keys are exchanged with the **wallet service**. The client's secret is generated locally and never leaves the client.

Two flows are defined:

- an HTTP confirmation page, for publicly accessible wallet services;
- a Nostr authorization URI, for mobile or self-hosted wallet services.

## Motivation

In the original NWC flow, the **wallet service** generates the **client**'s secret and the user must copy-paste a connection string into the client. This is error-prone and exposes the secret outside the client.

Letting the client create its own secret improves security and enables authorization-page UX where the user simply approves or declines a connection request.

## Authorization request

The client generates a fresh keypair and a random `state` value with at least 128 bits of entropy. The client then directs the user to the wallet service using one of the two flows below, with the following parameters:

- `pubkey` (HTTP flow) or the base path of the URI (Nostr flow): Required. The client's public key, hex-encoded.
- `state`: Required. Lowercase hex-encoded random value with at least 128 bits of entropy. The wallet service MUST return this value to the client as defined per flow, and the client MUST verify it.
- `relay`: Required in the Nostr flow, repeatable. URL of a relay where the client will communicate with the wallet service.
- `name`: Optional. The name of the client app.
- `icon`: Optional. URL of an icon of the client app to display on the confirmation page.
- `return_to`: Optional. URI to open after the connection is created.
- `expires_at`: Optional. Unix timestamp in seconds. The connection cannot be used after this date.
- `max_amount`: Optional. Positive integer limiting the cumulative outgoing amount, including fees, in millisatoshis per `renewal_period`.
- `renewal_period`: Optional. Renewal period for `max_amount`. MUST be one of `never`, `daily`, `weekly`, `monthly` or `yearly`, and MUST NOT be used without `max_amount`. `never` means the spending limit does not reset and is the default.
- `request_methods`: Optional. URL-encoded, space-separated list of request methods the client requires, for example `pay_invoice%20get_balance`.
- `optional_request_methods`: Optional. Same format as `request_methods`, for methods the client can operate without.
- `notification_types`: Optional. URL-encoded, space-separated list of notification types the client needs permission for.
- `isolated`: Optional. Makes an isolated app connection / sub-wallet with its own balance and only access to its own transaction list, for example `isolated=true`.
- `metadata`: Optional. URL-encoded, JSON-serialized metadata that describes the app connection.

The wallet service MAY ignore the optional parameters, subject to the requirements below. If `request_methods` is present, the wallet service MUST grant every listed method or decline the connection request. If `max_amount` is present, the wallet service MUST enforce it with the requested `renewal_period` or decline the connection request; it MUST NOT silently create a connection without the requested spending limit. The wallet service MUST ensure concurrent payments cannot collectively exceed `max_amount`. The wallet service MUST NOT grant request methods or notification types the client did not request. It MAY grant any subset of `optional_request_methods` and fewer notification types than requested. The client discovers the granted set from the `get_info` response.

The user MUST be presented with a confirmation page showing the requesting app, the requested methods, spending limit and expiry if present, and be able to approve or decline the connection.

## HTTP confirmation page

A wallet service MAY host a publicly accessible confirmation page that the client opens (for example in a webview or popup window).

If the user approves the request, a new connection is created for the client's public key.

### Communicating the result via popup/webview

The confirmation page SHOULD dispatch an event and post a message to the window and window opener (if present) so that the client can discover the pubkey and preferred relay URL of the wallet service:

```javascript
window.dispatchEvent(new CustomEvent("nwc:success", {
    detail: {
        relayUrl,
        walletPubkey,
        state,
        lud16, // optional
    },
}));

window.opener?.postMessage({
    type: "nwc:success",
    relayUrl,
    walletPubkey,
    state,
    lud16, // optional
}, "*");
```

If the user declines, the confirmation page MAY instead dispatch and post a message with type `nwc:declined`. The client MUST NOT assume approval without receiving `nwc:success` with a matching `state`.

If `return_to` was provided and no popup/webview is available, the wallet service SHOULD open the `return_to` URI with the `relay_url`, `wallet_pubkey`, `state` and optional `lud16` query parameters added.

### Example HTTP confirmation URL

`https://example.com/connections/new?pubkey=b889ff5b1513b641e2a139f661a661364979c5beee91842f8f0ef42ab558e9d4&state=9f2c4a...&name=Example%20App&max_amount=1000000&renewal_period=monthly`

## Nostr flow

The client generates an authorization URI with protocol `nostr+walletauth://` and base path its hex-encoded public key:

`nostr+walletauth://b889ff5b1513b641e2a139f661a661364979c5beee91842f8f0ef42ab558e9d4?relay=wss%3A%2F%2Frelay.example.com%2Fv1&state=9f2c4a...&request_methods=pay_invoice%20get_balance%20get_info`

To target a specific wallet, a `nostr+walletauth+<walletname>` scheme MAY be used.

The user opens the URI in the wallet service by scanning a QR code, handling a deeplink or pasting it in, and MUST be presented with a confirmation page.

If the user approves the request, a new connection is created for the client's public key. The wallet service MUST then broadcast its NWC info event (kind `13194`) to the relays specified in the authorization URI. This info event:

- MUST include a `p` tag containing the public key of the client, so that the client can discover the public key of the wallet service as the author of the info event;
- MUST include a `state` tag containing the `state` value from the authorization URI;
- MAY include one or more `relay` tags containing the recommended relay URLs of the wallet service. If provided, the client MUST use those relays for subsequent NWC communication instead of the ones from the authorization URI.

As required by NIP-47, the event also advertises the methods available to the connection in its content and the supported encryption schemes in an `encryption` tag. Because this flow implements NWC-08, the event SHOULD include `08` in its `extensions` tag.

For example:

```yaml
{
    "id": "<event-id>",
    "pubkey": "<wallet-service-pubkey>",
    "created_at": 1730000000,
    "kind": 13194,
    "tags": [
        ["encryption", "nip44_v2"],
        ["extensions", "08"],
        ["p", "b889ff5b1513b641e2a139f661a661364979c5beee91842f8f0ef42ab558e9d4"],
        ["state", "9f2c4a..."],
        ["relay", "wss://relay.wallet.example.com"]
    ],
    "content": "pay_invoice get_balance get_info",
    "sig": "<signature>"
}
```

The client subscribes to info events on its relays filtered by `#p` set to its own public key, and MUST verify that the `state` tag matches the value it generated before using the connection.

At this point, both the client and wallet service have all information required to communicate over NWC.

If the user declines, the wallet service publishes nothing. The client SHOULD treat the connection as declined after a reasonable timeout.

The `lud16` field MUST NOT be communicated via the NWC info event (kind `13194`), to avoid metadata leaks. The `result` object in the response to a `get_info` request SHOULD include `08` in its `extensions` array and MAY include a `lud16` field containing the lightning address.

## Security considerations

- The client's secret is generated locally and never leaves the client. Only public keys are exchanged during connection creation.
- `state` correlates the wallet service's response with the client's request. Without it, a third party observing the client's public key (for example on a public relay) could publish a spoofed info event or confirmation message pointing the client at an attacker's wallet service. Clients MUST generate a fresh, high-entropy `state` per request and MUST verify it.
- `name` and `icon` are client-supplied and unverified. Wallet services SHOULD present them cautiously to limit phishing.
- Spending limits are a security boundary only when enforced by the wallet service. Client-side limit tracking alone does not restrict what a compromised connection key can spend.
- Wallet services SHOULD use a unique wallet service public key per connection. Reusing one key for all connections leaks metadata: anyone who knows that key can filter relay traffic by it.
- Relays see metadata such as event kinds, timestamps, authors and `p` tags. Wallet services that run a relay SHOULD restrict event queries to filters containing a known author, `e` or `p` tag, so connection events cannot be enumerated by observers.

## Relationship to other specs

- NWC core defines the connection URI, the info event, and the `get_info` method that this specification builds on.
- [02](02.md) defines the notification types referenced by `notification_types`.
